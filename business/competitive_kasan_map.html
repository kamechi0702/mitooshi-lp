mitooshi Pro × 競合分析

競合 × 加算マッピング ／ mitooshi の勝ち筋

既存の記録自動化 SaaS が押さえている加算と、mitooshi が「カードめくりの先」で差別化できる領域を特定する。 結論：mitooshi は請求 SaaS の代替ではなく、行動データ層を補完する立ち位置。 既存 SaaS が構造的に作れない「子ども本人の操作ログ」を加算の根拠に変えるのが勝ち筋。

▶出発点：かめちの仮説

仮説

「カードをめくるだけでは補助ツールでしかなく、加算にならない。
別の価値が必要だが、それが何かをまだ見つけていない」

この仮説は正しい。カードめくり体験そのものは子どもへの提供価値であって、 事業所が加算を取る根拠にはならない。本書では「めくり体験の副産物」として何が生まれるかを掘り下げ、 そこに事業所価値（＝加算根拠）を見出す。

マトリクスから見える事実

請求・出退・送迎の領域は HUG 等が完全に押さえている。ここで戦うのは無謀。 一方、「支援の中身」「個別性」「行動の経過」を必要とする加算は競合の手薄。 mitooshi が独占できる可能性がある領域は 集中的支援加算・家庭連携加算の2つで、 差別化できる加算は 個別サポート加算Ⅰ・専門的支援実施加算・強度行動障害児支援加算・モニタリングの4つ。

03空白地帯の特定

競合がカバーしていない（または弱い）領域を構造的に整理する。

1「支援の中身」の客観記録が手薄
既存 SaaS の支援記録欄は「自由記述」で、「今日は◯◯をしました」レベル。 実地指導で「何を、どう、どの程度の効果で支援したか」を問われると具体性が出ない。 個別支援計画と日々の記録の整合性も担保しづらい。
2子ども本人の参加証跡がない
記録は大人の視点で書かれる。「本人参加型支援」の証跡として、 子ども本人が何をしたかの客観データは既存 SaaS には存在しない。 これが 個別サポート加算Ⅰ や 強度行動障害児支援加算 の質的要件で減算される一因。
3行動の時系列変化が定量化されない
「3か月でどう変化したか」を文章で書くしかない。 集中的支援加算の効果検証は本来定量データが望ましいが、既存 SaaS では作れない。 新設加算ゆえに業界全体で算定率が低く、空白地帯。
4家庭支援の連続性が断絶
既存 SaaS の保護者連絡機能は「お知らせ送信」止まり。 家庭で実際にどんな支援が行われたか、その効果はどうだったかの双方向のデータ連続性はない。 家庭連携加算の月4回フル算定が難しい一因。
5引継ぎ資産が持ち運べない
進級・進学時の保育・教育等移行支援加算では、引継ぎ内容の具体性が問われる。 既存 SaaS では「引継ぎ書」を新規作成する必要があり、児発管の時間が取られる。 子どもの個別性が「持ち運べる資産」として残っていない。

04mitooshi だけが生成できる独自データ

「カードをめくる体験」の副産物として、他 SaaS が構造的に作れない4種類のデータが生まれる。

4種類の独自データ

  1. ① 子ども本人の操作ログ ：誰が、いつ、どのカードをめくったか。主体的参加の客観証跡になる。職員が代行操作した場合と区別できる。
  2. ② シーン × カード組み合わせ ：「Aくんは登園シーンに3枚で OK、Bくんは10枚必要」など個別性が定量化される。 個別支援計画の「本児の特性」記述の素材になる。
  3. ③ 行動前後の介入文脈 ：パニック前にどのカードを示したか、切り替え時にどの順序で見せたか。 自由記述では再現できない解像度の支援プロセス記録。
  4. ④ 家庭 × 施設の連続性ログ ：施設で組んだカードを家庭でも使う、家庭での反応を施設に持ち帰る。 双方向のデータ連続性は toC × toB を持つ mitooshi 独自。
核心の発見

「カードめくり」自体は子どもへの体験価値だが、その操作ログ＝事業所への加算証跡になる。 これが「もう一つの価値」の正体。
競合 SaaS が「大人が書く記録」しか作れないのに対し、mitooshi は「子どもが残すデータ」を生成する唯一のツール。

05価値の二層構造

mitooshi の価値は2層で考えると整理しやすい。

Layer 1 ／ 子ども・保護者向け

カードめくり体験

子どもの不安を減らし、保護者の声かけ疲れを軽減する。UX としての提供価値。

  • めくる楽しさ・自分で進める感覚
  • シーン別ボードによる予測可能性
  • 保護者と一緒に作る共同体験
Layer 2 ／ 事業所向け

行動データ生成エンジン

めくり体験の副産物として「加算根拠データ」が自動で蓄積される。事業価値としての提供価値。

  • 子ども本人の操作ログ＝主体的参加の証跡
  • シーン × カードの組み合わせ＝個別性の定量化
  • 行動前後の介入文脈＝支援プロセスの記録
  • 家庭 × 施設の連続性ログ＝双方向データ

重要なのは Layer 1 を充実させると Layer 2 が自動で強くなる構造。 機能追加するときは「子ども体験を良くする」と「事業所証跡を強くする」の両方を満たすかで判断する。

06勝ち筋3パターン

独自データから生まれる3つの差別化シナリオ。

Path A：集中的支援加算の効果検証ツール ニッチ独占
狙う加算

集中的支援加算（1,000単位／日・新設）

差別化の核

3か月の行動変化グラフを自動生成。算定要件の「効果検証」を満たせる唯一のツール

ポテンシャル

1事業所あたり月4万円規模だが、業界全体で算定率が低く伸びしろ大

Path B：家庭連携加算の連続性ツール 独自・推奨
狙う加算

家庭連携加算（300〜1,000単位 × 月4回上限）

差別化の核

toC × toB の双方向データ連続性。競合 SaaS では構造的に真似できない

ポテンシャル

1事業所あたり月7万円規模。toC アプリの普及がそのまま toB の価値を押し上げる

Path C：個別性の客観化ツール 横断・推奨
狙う加算

個別サポート加算Ⅰ／専門的支援実施加算／強度行動障害児支援加算／モニタリング

差別化の核

「個別性は児発管の文章力次第」という業界課題に対し、行動データで客観化

ポテンシャル

複数加算に横断的に効くため、1事業所あたり月15万円規模の取りこぼし防止が見える

07戦略的推奨

結論：Path B + Path C を主軸、Path A は導入後の上振れ

Path B（家庭連携）と Path C（個別性の客観化）を 提案の中心に据え、 Path A（集中的支援）は 導入後の追加価値として後出しにする。

ポジショニング・ステートメント

ポジション

mitooshi Pro は 請求 SaaS の代替ではない。HUG 等の業務統合 SaaS と並列で導入する補完ツール。 「請求事務は HUG、支援の中身は mitooshi」という分業が自然な姿。
存在意義は 「子どもが残すデータで、加算の質的要件を満たす」こと。

セールス・トーク（HUG 既導入施設向け）

セールス・トーク

「HUG さんで請求事務はバッチリやられてますよね。mitooshi はそれを置き換えるものではなく、 HUG だと書ききれない『支援の中身』の証跡を作るツールです。 子ども自身がカードをめくった事実、その日に使ったカードの組み合わせ、それが個別支援計画と一致しているか。 実地指導で『個別性』を問われたときに、HUG の自由記述だけでは弱い領域を、mitooshi のデータで補強する。 そういう関係性です」

4つの設計指針

  1. 「請求機能は作らない」 ：HUG の領域に踏み込まない。代替ではなく補完であることを徹底する
  2. 「子どもが触る」を死守する ：操作主体ログこそ独自価値の源泉。職員代行 UI は警戒（出すなら「代行」と明示）
  3. 「家庭 × 施設の連続性」を機能の柱に置く ：toC mitooshi との連携機能（カード共有・反応共有）を Pro の中核機能にする
  4. 「行動データの可視化」を提供する ：めくり所要時間・自発めくり率・離席頻度などの定量グラフを児発管に届ける
避けるべきポジショニング 「療育記録 SaaS」と名乗ること。HUG 等と正面衝突して負ける。 「視覚支援ツール × 行動データ」「子どもが残すデータの療育プラットフォーム」 のような独自カテゴリを作る言い方を選ぶ。

08検証すべき仮説

本書は仮説ベース。Discovery で検証すべき項目を明示しておく。

  1. HUG 等を導入している事業所が「支援の中身の記録」に課題を感じているか（補完関係の前提）
  2. 「個別性が薄い」という実地指導の指摘事例が実在するか（差別化価値の前提）
  3. 集中的支援加算の算定見送り率は実際どれくらいか（Path A の前提）
  4. 家庭連携加算の月4回フル算定率はどれくらいか（Path B の前提）
  5. 子どもが触ることへの抵抗が現場にどれくらいあるか（操作ログ独自性の前提）
  6. HUG 等と並列導入する月額予算枠は確保可能か（価格戦略の前提）

特に重要なのは 1.（補完関係の前提）。 HUG ユーザーが「HUG で十分」と感じているなら mitooshi の隙間はない。 実地指導での減算経験・個別性の悩みが具体的に語られるかがポイント。
