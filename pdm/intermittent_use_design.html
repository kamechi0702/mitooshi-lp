mitooshi Pro ／ Intermittent Use Design

触らない日問題：サンプリング型データ収集の設計

「子どもや保護者が mitooshi を毎日触るとは限らない」という現実を踏まえ、 稀な接触でも加算根拠を確実に作るための設計。 実は軽度向け加算は「毎日触る必要がない」構造になっている。

▶課題の整理

かめちの問い

「療育と家庭で必ず触るとは限らない可能性もある。
その場合を考慮して、加算記録できるかどうかも詳細に教えてほしい」

現実認識

  • 家庭：保護者の生活ペース。毎日 mitooshi を触るとは限らない。月数回〜週数回が現実的。
  • 施設：カリキュラムの中で個別ボードを使う日と使わない日がある。職員の余裕にも左右される。
  • 子ども：気分・体調によってめくるかどうかが変わる。強制はできない。

にもかかわらず加算根拠は確実に残したい。これが両立可能か？ 結論：Option B（軽度向け加算）の場合、両立可能。

01重要発見：軽度向け加算は「毎日触る必要なし」

ファクトチェックで Option B（軽度向け加算）に絞った結果、対象となる加算はすべて「日次」ではなく「イベント駆動」であることが判明。 つまり毎日触る必要がない。

核となる気付き

Option A（重度向け：個別サポートⅠ・強度行動障害）は日次算定のため毎日触る必要があった。
Option B（軽度向け：家庭連携・移行支援・関係機関連携・専門的支援実施）はイベント駆動算定のため、必要な時だけ触ればよい。
この違いが「触らない日問題」を構造的に解決する。

結論

Option B のすべての加算で、「特定の日・時に集中して触れば足りる」。 毎日の継続使用は理想だが、必須ではない。 連続観察ではなく、サンプリング型データ収集で十分加算根拠になる。

03サンプリング型データ収集モデル

1か月（30日）の中で、いつ・誰が・どれくらい触れば加算が成立するかを可視化。

パターン A：理想型（毎日触る・連続観察型）

家庭
施設
使用日 面談 専門職立合 非使用日

毎日触る理想型。データ密度が最高、ただし現実的には保護者・職員ともに継続が難しい。

パターン B：サンプリング型（推奨・現実解）

家庭
施設
使用日 面談 専門職立合 非使用日

家庭：週1回程度（月5回）／ 施設：月数回（イベント駆動）／ 面談月1回／ 専門職立合月4回。 これだけで Option B のすべての加算が算定可能。

サンプリング型の経済インパクト

家庭月5回 + 施設月8回 = 合計月13回の接触で、家庭連携加算 (4回×600=2,400単位)・関係機関連携 (250)・専門的支援実施 (4回×150=600単位)・モニタリング データ確保がすべて達成される。
→ 単純計算で 3,250単位 ≒ 月32,500円のポテンシャル（地域加算別途）。

045つのフォールバック設計

子ども・保護者・職員が触らない日でも、加算根拠が劣化しない仕掛け。

1
集中接触モード（Burst Mode）

「面談前1週間だけ集中的に触る」「専門職立合日とその前後のみ触る」など、 イベント駆動で接触を集める運用。普段は触らなくてOK。

UI挙動
次回面談まで X 日と通知。「面談で振り返れる材料を用意しよう」と促す。
該当加算
家庭連携加算（面談前バースト）
専門的支援実施加算（立合時バースト）
2
紙＋写真フォールバック（Paper Bridge）

触らない日の紙メモ・連絡帳・絵カードを写真撮影して mitooshi にアップ。 OCRで日付・児童名を自動推定し、タイムラインに紐付ける。

UI挙動
ホーム画面に「📷 紙の記録をアップ」ボタンを常設。1タップで撮影 → 自動紐付け。
該当加算
モニタリング（過去データの追補）
関係機関連携加算（紙の連携書類）
全加算の補強証跡
3
既存データ連携（External Data Hooks）

HUG・カイポケ等の既存記録データ、保育園からの連絡帳、相談支援事業所からの計画書など、 外部データを取り込んで「mitooshi 接触相当」として扱う。

UI挙動
HUG / カイポケ から定期取り込み（CSV／API）。連携状況をダッシュボード表示。
該当加算
モニタリング全般
関係機関連携加算
個別支援計画見直し時の素材
4
最小1回有効設計（Minimum Viable Touch）

1回の接触＝1つの加算根拠として独立させる。 「全くゼロ」と「1回でもあり」の差を最大化。

UI挙動
接触1回ごとに「✓ 加算根拠が1件追加されました」と即時フィードバック。
小さな前進を可視化して継続を促す。
該当加算
家庭連携加算（評価マーク1個でも有効）
専門的支援実施加算（立合1回でも記録化）
移行支援加算（カードセット出力1回）
5
算定可能性アラート（Eligibility Watcher）

児発管ダッシュボードに、各加算の算定可能性をリアルタイム表示。 「あと2回触ると面談データが充実」「専門的支援実施加算 残3回算定可」と能動的に提示。 取りこぼし防止のレバーとして最も重要。

UI挙動
毎朝・週1の自動通知。各加算の「算定済 / 算定可能 / 不足」を3色で表示。
該当加算
Option B 全加算
特に月4回上限のあるもの（家庭連携・専門的支援実施）

このUIが解決する問題

従来：月末になって「算定できる加算を取り逃した」と気付く取りこぼしが頻発。
mitooshi：リアルタイムで算定可能性を可視化し、月内に行動を促す。
→ これだけで 取りこぼし率を 30% → 10% に圧縮できるのが提案価値の核。

06算定の最低ライン

「これ以下になると算定できない」最低限の接触量を加算別に明示。

加算 最低接触ライン これ以下だと…
家庭連携加算 家庭で月1回以上の使用 + 月1回の面談 面談時に「具体的に話せるネタ」が無くなる → 算定見送り
保育・教育等移行支援 引継ぎ時にカードセット1セット出力 カード資産がない → 引継ぎ書を新規作成する負担に戻る
関係機関連携加算 月1回の共有ログ 共有エビデンス不足 → 紙資料に依存
専門的支援実施加算 立合時のカード使用ログ1回 専門職関与の客観証跡なし → 紙書類で記録要
モニタリング 3か月で5回以上の接触 個別性の客観データ不足 → 文章のみで個別性訴求
注意：「算定できない」ではなく「mitooshi の貢献度が下がる」

最低ライン以下でも加算自体は事業所が紙書類で取れる。 ただし mitooshi の「証跡を強くする」「取りこぼしを防ぐ」価値が発揮できなくなる。 事業所は mitooshi を「継続する意味がない」と判断するリスクがある。

07PRD への反映項目

必須機能（Phase 1）

  • 算定可能性ダッシュボード：各加算の月内達成状況を3色で表示
  • 面談前リマインダー：面談前1週間に家庭側通知「振り返れる材料を準備」
  • 紙写真アップロード：OCRで日付・児童名を自動推定して紐付け
  • 1回接触の即時フィードバック：接触ごとに加算根拠1件追加表示

連携機能（Phase 2）

  • HUG / カイポケ CSV取り込み：外部データを mitooshi タイムラインに統合
  • 連携先（医療・保育園）への共有 URL 発行：関係機関連携加算の証跡化
  • 引継ぎ書出力：本児のカードセット + 使用ガイド + 効果的シーン

運用ガイド

  • 「毎日触らないとダメ」と説明しない：営業時に「月数回でも算定可能」を明示
  • 面談・立合・連携を「mitooshi の主戦場」と位置付ける：日常運用ではなくイベント時に集中
  • 取りこぼし防止アラートを継続提供：月末ではなく月内に行動を促す
戦略的意味

「触らない日問題」は、Option B 戦略の弱みに見えて実は強み。 「日々の業務に侵食しない・必要な時だけ使う」という導入のしやすさを生む。 競合 SaaS（HUG等）は日次入力前提のため、施設の業務負担を増やす。 mitooshi は「軽量・イベント駆動・取りこぼし防止」という独自ポジションが取れる。
